# 公网防护接入与管理方交接

更新：2026-11-23。正式 DNS、代理、防火墙和正式服务均未变更。

## 当前进度

- 网站侧按需验证已接入页面表单和 JSON 登录接口，使用隔离环境完成规则、权限和故障测试。当前预览使用 Cloudflare 官方演示密钥并显示演示标记，只演示流程，不判断访客是否为机器人。
- 已确认：同一账户在 5 分钟窗口内密码/TOTP 失败 3 次后追加验证，失败 8 次暂停至该窗口结束；同一可信来源 IP 失败 30 次后追加验证，不直接封禁整个共享出口。成功登录清除该账户失败计数，不清除整个出口的其他失败记录。
- Cloudflare 不可用、响应异常或校验容量已满时，暂停已触发验证的登录并返回 503、`Retry-After: 30`；未触发验证的正常登录不请求 Cloudflare。验证码失败不继续检查密码，也不继续累积密码失败次数。并发密码检查预占名额，不能用同时提交突破每账户 8 次预算。
- 用户确认域名或前置代理由其他人管理。Cloudflare 边缘 WAF、限流、DDoS 及真实 IP 链路，必须由管理方配置并共同验证。当前尚未取得配置和生效证据。
- 保持现有域名、API BaseURL、路径、用户密钥和内部预注册方式；不采购套餐，不增加自助注册。

## 请管理方先确认的资料

1. 网站和模型 API 当前使用的域名、DNS 管理方、代理入口及源站连接关系；是否已经过 Cloudflare，以及所属套餐。
2. 若尚未接入，评估在现有管理账户下启用代理的方式。先核对整区 DNS、邮件记录和现有证书，不直接替换名称服务器；不要让用户重复注册、购买服务或创建冲突配置。
3. 在管理方账户创建 Turnstile 的 Managed 类型组件，登记准确的网站域名，关闭预清除（本方案仅验证登录）。测试和正式组件、密钥分开；正式组件不允许 localhost。
4. Site Key 可以提供给网站维护方；Secret Key 通过双方认可的私密配置渠道交付。不要放到聊天、Git、截图或代理访问日志中，也不需要交付管理方账户密码或全局 API Key。

Turnstile 可独立于 Cloudflare DNS 使用，网站侧验证可以先接入；它不能替代边缘 WAF 或 DDoS。组件创建和账户要求见 [Turnstile 官方说明](https://developers.cloudflare.com/turnstile/get-started/)。

## 边缘侧配置范围

| 项目 | 配置与验收要求 |
| --- | --- |
| HTTPS | 保留既有域名和 URL，确认源站证书有效，使用 Full (strict)，避免 Flexible 引起协议混乱；改动前保存当前配置。 |
| 基础 WAF | 确认免费托管规则实际启用并查看安全事件；先验证正常登录、文件上传、OAuth 回调和模型调用，仅对有证据的误拦作最小范围调整。 |
| DDoS | 确认网站流量经过代理并启用现有套餐提供的默认防护；不通过攻击正式站来验收。普通网站代理不等于整台源站所有端口受保护。 |
| 登录限流 | 只匹配下面两个登录路径。免费版只有按 IP 计数，无法识别同一校园网内不同账户；阈值须结合共享出口人数确认，不能照抄本站的每账户失败次数。保存规则 ID、动作、阈值和回退方式后再启用。 |
| 模型 API | `/api2api/v1/` 不启用浏览器挑战，不纳入登录限流。保留密钥认证、额度及可信来源 IP 限制；不新增未经确认的账户 RPM 或并发限制。 |
| 缓存与流式响应 | 不缓存登录、鉴权和私人数据响应；模型 API 不缓存、不变换响应、不缓冲 SSE，保留断开取消。排查现有全站缓存、内容变换或挑战规则的影响。 |
| 机器人保护 | 不全站启用免费 Bot Fight Mode，也不全站开启 Under Attack 挑战；这些设置可能影响 SDK 和 Agent。 |

免费限流规则可以使用的路径表达式：

```text
http.request.uri.path in {"/login" "/api/auth/login"}
```

此表达式不包括模型 API。免费套餐的该规则不能用方法、Host 或响应状态作为计数条件，GET 登录页也计数；同一区域内其他域名的相同路径也可能匹配。管理方须检查这些影响后决定启用范围和阈值。免费版当前支持 1 条规则、10 秒统计窗口和 10 秒拦截窗口，不能把本站的 5 分钟账户窗口原样填进去。[套餐与参数限制](https://developers.cloudflare.com/waf/rate-limiting-rules/)

Cloudflare 提供自动 DDoS 缓解，实际覆盖仍取决于流量入口。[DDoS 官方说明](https://developers.cloudflare.com/ddos-protection/)。Bot Fight Mode 的挑战和路径豁免限制见 [官方说明](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)。

## 可信来源 IP 与源站访问

本站继续以已校验的连接来源为准，不直接信任客户端传入的 `CF-Connecting-IP` 或 `X-Forwarded-For`。先由管理方画出实际的 Cloudflare → 前置代理 → 本站链路，再改代理配置：

1. 前置代理只在连接来自 Cloudflare 官方网络范围且入口可信时接受其真实 IP 头；直接连接不能携带自选来源 IP 绕过限制。
2. 清除外部伪造的来源头，将可信的调用者 IP、原网站 Host 和 HTTPS 协议转交本站。不要把 Cloudflare 节点或代理 IP 当成所有用户的 IP。
3. 本站 `MAILAPI_TRUSTED_PROXY_IPS` 只列出紧邻本站的可信代理地址，不设为 `*`。现有 `ProxyIngress` 接收精确 IP，不接受 CIDR，不要直接粘贴 Cloudflare 网段。
4. 网络层仅放行实际前置代理访问应用端口；面向 Cloudflare 的入口限制为可信来源，条件允许时采用专用证书认证的回源或 Tunnel。保留独立管理通道，先验证后限制，避免断开现有代理。
5. 同一账户从两个受控客户端访问时，确认本站看到不同的正确来源；伪造来源头应无效。模型密钥的 IP 限制也必须通过此链路验证。

[Cloudflare 来源头的语义与 Worker 注意事项](https://developers.cloudflare.com/fundamentals/reference/http-headers/)、[Cloudflare 官方 IP 范围](https://www.cloudflare.com/ips/)。不要仅凭响应中出现 `cf-ray` 就判定源站访问限制和真实 IP 已正确配置。

## 网站侧已准备的校验基础

`mailapi_shared/login_protection.py` 的校验器只向固定 HTTPS Siteverify 地址提交令牌和可信来源 IP，禁止重定向和环境代理，限制响应为 8 KiB，网络超时为 5 秒，同时最多进行 4 个校验请求。不向 Cloudflare 发送用户名、密码、TOTP 或模型内容。

校验成功必须为布尔值 `true`，并匹配预配置域名及 `action=login`；验证失败不能视为正常登录成功。令牌在本进程内立即登记，避免供应商重复核销状态传播期间被同时使用。此状态有 5 分钟有效期和容量上限，服务重启或多进程不共享；供应商自身的有效期和核销校验仍然必要。目前本站为单进程，不能据此直接增加 worker。

Cloudflare 官方演示密钥仅允许在显式测试模式成对使用，永远不应放入正式配置。官方演示组件重复生成同一个固定令牌，校验返回 `example.com` 且不含 action；代码只对这一明确的演示组合处理其特殊行为。真实密钥始终校验域名和 action，演示验证通过不等于真实站防护通过。[服务端校验](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)、[官方测试密钥与限制](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)

网站组件只在失败达到阈值后加载。验证过期或加载失败时可以重新加载；不会自动重复提交密码。关闭前端脚本或直接请求登录接口也必须通过后台验证。管理员原有 TOTP 和安全会话 Cookie 继续生效，不保存密码或验证令牌到浏览器存储。

### 配置与停用

测试使用 `.env.test` 的 `TEST_TURNSTILE_SITE_KEY`、`TEST_TURNSTILE_SECRET_KEY` 和 `TEST_APP_BASE_URL`。正式部署准备使用独立 `.env` 的 `TURNSTILE_SITE_KEY`、`TURNSTILE_SECRET_KEY` 和 HTTPS `APP_BASE_URL`；当前没有写入正式配置或重启正式服务。

两个密钥都为空时保持原登录逻辑（原有每账户 8 次、每 IP 30 次尝试限制），不会加载验证组件；任一密钥有值时必须全部配置，错误配置拒绝启动，避免意外悄悄关闭验证。测试配置不读取正式 Turnstile 密钥，网页只获得公开 Site Key。故障回退需要维护方明确撤回两个配置并重启对应环境，不提供客户端可绕过的开关；退回原逻辑仍有本地限流。

## 接入顺序与回退

1. 已确认登录阈值和故障策略，完成网站登录路由与按需组件加载。先用官方演示密钥验证本地流程；正常登录不加载第三方挑战脚本，页面表单与 JSON 登录接口都由后台检查。
2. 管理方提供测试组件及准确域名，先在可恢复的测试入口验证真实密钥、超时、过期、重复验证和共享出口体验。正式服务继续保持当前状态。
3. 管理方配置测试入口的 WAF、限流、代理和来源 IP，保存配置前后版本及规则 ID。验证正常上传、OAuth、附件、财务数据权限，以及 SDK 普通和流式调用。
4. 用同一模拟上游、同一请求条件对比接入前后的首段延迟、错误率和流式即时交付。尚无边缘联通测试结果，不预先承诺零延迟。
5. 测试通过后提交具体的正式配置变更和回退结果，再确认正式切换。每次只改一个环节；出现误拦先撤回对应新增规则，保持原入口可恢复。

正式切换前，管理方至少提供：实际代理链、组件已登记域名、规则 ID 与参数、真实 IP 和源站限制验证、流式调用结果、DNS/代理原配置及恢复方式。密钥不放入验收记录。
