## 待修复或加强的项目

### 1. 出站请求的令牌重定向与响应大小保护（中优先级）

`mailapi_shared/application.py:1446` 的 `http_json()` 和
`mailapi_shared/mail_providers/outlook.py:153` 的 `graph_request()` 使用默认 `urlopen()`，
没有显式限制跨域重定向，成功和错误响应也直接调用无大小上限的 `read()`。

使用假 Bearer 令牌在本地 Python 3.14.5 的默认重定向处理器中复现了跨主机跳转时保留 Authorization。
这意味着客户端缺少应用自己的令牌跨域保护；风险的触发条件是上游发生跨域跳转，并非已发现真实令牌外泄。
上游返回异常大的响应或持续传输时，还可能占用过多内存或长时间占据工作线程。

建议禁止自动重定向，或对每次跳转严格校验 HTTPS 和目标主机；同时限制成功、错误响应的总字节数，
设置累计读取时限。Coding Plan 查询已经有禁止重定向、响应大小和超时控制，可参考其实现。
参考：[Python urllib.request](https://docs.python.org/3.14/library/urllib.request.html)。

### 2. 账户写入会阻塞异步事件循环（中优先级，已复现）

`mailapi_shared/accounts.py:117` 的修改密码，以及 `:133`、`:141`、`:154` 的账户创建、批量创建和修改路由，
在 `async def` 中直接调用密码推导与同步文件写入。批量创建还会在存储锁内多次执行 PBKDF2。

本地 uv 环境中，使用独立 FastAPI 测试应用和 8 个模拟账户，批量创建请求耗时约 0.367 秒，
原本每 5 毫秒执行的心跳出现约 0.352 秒间隔，确认此时事件循环被阻塞。
这会拖慢同一进程的其他请求；账户操作也缺少与登录相似的频率控制。

建议把同步工作移出事件循环，缩短锁内的密码计算和磁盘操作，并对敏感写入设置合理限流。
还需检查登录中间件等异步代码对同一同步锁的获取，不能只把写入简单搬到线程就视为解决。
参考：[Starlette 线程池说明](https://starlette.dev/threadpool/)。

### 3. 敏感运行资料尚未统一加密（中优先级，防御加强）

网站登录密码已经哈希，但 GPT 密码、2FA、管理员 TOTP 密钥、API Key 和 OAuth 令牌仍需以可读形式保存。
恢复点已有加密，不代表当前生效配置也已加密。文件权限能限制其他操作系统账户读取；运行目录或备份泄露时，
这些凭据仍可能被获取。

建议独立设计凭据加密、密钥隔离与轮换、加密备份和恢复演练。数据库迁移本身不会自动完成这些保护。
参考：[OWASP 加密存储建议](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)。

### 4. 磁盘与进程运维（需跟进）

服务器 `/data1` 使用率为 96%，仍有约 323 GB 可用，尚未发现磁盘已满；应增加容量与 inode 告警，
并为历史、图片和备份制定保留策略。不能直接删除现有授权文件或账号历史腾空间。
正式进程位于 `mail:0.0` 的 tmux 会话中；本次未确认有崩溃自动重启、外部健康监控和备份恢复演练。

建议在单进程约束下完善服务托管与监控，不能直接增加 worker；JSON 存储仍存在跨进程并发写入限制。

- 8000 当前监听所有 IPv4 接口，应用层已拒绝非可信来源；服务器当前用户无法读取 nftables/iptables 规则，
  未确认网络层是否也仅放行反代。反代位于另一台机器，不能直接把监听地址改成回环而使反代断连。
- 未取得反代配置，不能确认其总连接数、请求频率限制，以及 OAuth 查询参数的访问日志脱敏。
- 主机还存在本项目以外的监听端口，本次未测试其他服务，也未扫描整个操作系统的漏洞。
- 按用户名共享的登录限流会在连续 8 次尝试后使该用户名进入最长 5 分钟等待，存在被定向干扰登录的可用性取舍。
- CSP 当前主要限制嵌套、base 和 object，尚未严格限制脚本来源；可在后续集中处理内联脚本时加强。
