# API 转发模拟压测与优化（2026-11-22）

本次在 213（mil-id1）建立独立临时测试副本，使用现有 mailapi-secure Conda 环境、原生 NewAPI v1.0.0-rc.51 Linux x86_64 官方二进制，以及全新模拟网站账户、密钥和数据库。所有监听仅绑定 127.0.0.1，未调用实际模型服务商，未同步或重启正式服务。本地测试预览保留原有数据并加载了最终优化。

## 测试条件与口径

- 主机 32 个逻辑 CPU，约 252 GiB 内存；这是共享服务器上的顺序测试，不是独占主机基准。
- 使用完整网站应用及原有中间件，HTTP 并发限制保持 128；网站至 NewAPI 连接池保持 200；NewAPI 使用原版默认 SQLite 连接设置，未启用 Redis、鉴权缓存或批量延迟记账。
- 请求包含约 8 KiB 模拟提示内容。模拟上游等待 200 ms 后开始发送内容；短流每 100 ms 一段，共 10 段；长流每 500 ms 一段，共 60 段。每段内容为 64 字节，usage 为明确的模拟值。
- 短流按 30/50/100 个持续客户端闭环运行 20 秒，停止补充新请求后等待在途请求完成；长流每档同时发出一组请求，保持约 30 秒。
- 延迟从客户端发起请求计时：TTFT 是收到首段非空模型内容的时间，包含模拟的 200 ms；P95 使用排序后下标 floor((n-1)*0.95)，不表示最坏情况。全部内容须符合预期字节数并有 [DONE] 才计为成功。
- 每 200 ms 请求网站 /login，检查 API 压力下网页响应；每 100 ms 从 /proc 读取各进程 CPU、RSS、文件句柄和 write_bytes。CPU 百分比以单个逻辑核为 100%，32 核主机的总量为 3200%。
- 同机也运行模拟上游和发生器，资源分别记录。冷建连、同步突发、共享主机调度及发生器开销均包含在结果内；控制组的首段长尾也明显，不能把全部延迟简单归因于网站或外推到真实外网模型。

## 短流优化前后

| 并发 | 基线成功/请求 | 优化成功/请求 | TTFT 中位数 ms（前 → 后） | TTFT P95 ms（前 → 后） | 网页 P95 ms（前 → 后） |
|---|---:|---:|---:|---:|---:|
| 30 | 454/454 | 474/474 | 370.83 → 341.89 | 591.95 → 580.61 | 91.57 → 15.21 |
| 50 | 642/642 | 764/764 | 515.99 → 343.30 | 908.28 → 676.74 | 241.04 → 22.10 |
| 100 | 746/747 | 1014/1014 | 1385.67 → 355.09 | 1653.69 → 1816.24 | 724.46 → 61.14 |

100 并发基线有 1 次 503（1/747，约 0.134%），网站转发用量仅新增 746 行，与在入口被拒绝相符；优化后 1014 次均成功且用量行数完全对应。入口 128 限制未放大，因此这轮零错误不能证明所有后续突发都不会触发入口保护。

100 并发短流吞吐从 33.70 提升到 45.87 请求/秒（约 36.1%）；网页 P95 降低约 91.6%。网站 write_bytes 按请求归一化从 130.82 降到 13.84 KiB/次，减少约 89.4%。

100 并发 TTFT 中位数明显改善，但 P95 从 1653.69 增至 1816.24 ms，未消除首段长尾；不把中位数改善表述为所有延迟都改善。

## 资源占用（最终采用配置）

以下仅统计网站与原生 NewAPI；发生器和模拟上游另列在原始 JSON。RSS 为采样峰值与结束样本的较大值；两进程各自峰值相加是保守上界，不是精确同一时刻的峰值。

| 场景 | 网站平均 CPU（单核=100%） | NewAPI 平均 CPU | 网站 RSS MiB | NewAPI RSS MiB |
|---|---:|---:|---:|---:|
| 100 并发短流 | 102.92% | 164.21% | 153.32 | 168.29 |
| 100 并发长流 | 27.12% | 15.59% | 154.82 | 162.86 |

100 并发短流两服务平均合计约 2.67 个逻辑核，约为 32 核总量的 8.35%，RSS 峰值之和约 321 MiB。线程化后每秒可处理更多请求，CPU 使用会随吞吐增加；不能据此声称 CPU 百分比也下降。100 ms 采样存在较高瞬时峰值，详情保留在原始数据。网站与网关没有出现持续内存增长到资源上限的现象，但本轮时长不足以排除慢性泄漏。

## 已确认的瓶颈及采用的修改

1. 原转发协程直接做同步 SQLite 鉴权、配置查询和用量落库，数据库等待会阻塞网页事件循环。新增的阻塞数据库回归测试可稳定复现：鉴权或记账被挂起时，原代码使独立心跳请求也无法返回；优化后心跳可立即完成，调用结束后记账仍完整。
2. 请求连接反复成为最后一个 SQLite 连接，导致 WAL 反复收尾和重建，网站每次调用约 131 KiB 写盘。现在测试应用保留一个不持有读事务的空闲连接，退出时关闭；测试验证 WAL inode 跨请求复用、正常退出后关闭最后连接并保留完整数据。
3. 已将转发鉴权/配置查询及成功、失败、流中断的用量写入移至有界 AnyIO 工作线程池，仍等待记账完成。没有跳过权限校验、缓存密钥结果或延迟批量计费。
4. 原生 NewAPI 连接池缩为 8 的额外实验：100 并发短流 TTFT P95 为 1249.75 ms，但中位数变为 719.41 ms、吞吐为 38.10 请求/秒（原优化配置 45.87）；长流 P95 仍为 2170.20 ms。因此不采用该池设置，也不宣称它全面改善性能。
5. 还存在网关与同步突发产生的首段长尾。固定版本的 [OpenAI 流处理源码](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.51/relay/channel/openai/relay-openai.go#L115) 会在收到下一帧后再发送前一帧，这会附加与出帧间隔相关的延迟；不能把所有长尾都算成网站数据库等待。本次保留原生引擎语义，没有自行修改 usage/尾帧处理。

## 上游限制 20 并发

| 本站并发 | 上游实际峰值 | 成功 | 返回 429 | 用量记录行数 |
|---|---:|---:|---:|---:|
| 30 | 20 | 20 | 10 | 30 |
| 50 | 20 | 20 | 30 | 50 |
| 100 | 20 | 20 | 80 | 100 |

这组 429 是刻意模拟的服务商限流，不能混进正常容量测试的基础设施错误率。本地 HTTP 连接池和入口设置不会自动跟随服务商降为 20；真实能同时生成的数量受上游限制。最终 100 请求突发有 20 个成功、80 个收到 429，上游峰值始终为 20。本站透传 429，没有自动排队或反复重试；原生网关返回 Retry-After 时网站层会透传该字段。多个渠道能否分担还取决于各自的模型权限、额度和限额。

- 正式服务 PID 与启动时间保持一致，两项正式代码基线校验一致，正式 /login 返回 200；审计时无遗留压测 worker。本地正式数据基线 50 个文件未变化，原本地测试数据和预览保留。
- 当前优化回归：本地 uv 环境 82 项相关后端测试、116 项前端测试通过。
- 原始数据：[基线](api-relay-2026-11-22-baseline.json)、[最终采用优化](api-relay-2026-11-22-optimized.json)、[未采用的 8 连接池实验](api-relay-2026-11-22-pool-8.json)、[隔离核对](api-relay-2026-11-22-isolation.json)。
- 脚本：[benchmark_api_relay.py](../../scripts/benchmark_api_relay.py)。官方 Linux 二进制 SHA-256：`a42f4559790021ffec8a609182cf142b430f822cf420270105422c800c519157`。
- 服务器使用既有 Conda 环境；本地验证使用既有 uv 环境。新环境只接收不含 .env/数据库/凭据的代码副本，脚本新建私有临时目录、随机模拟凭据并在退出时结束子进程和移除测试数据。

在隔离代码副本、现有服务器 Conda 环境中执行：

```sh
python scripts/benchmark_api_relay.py --binary /path/to/new-api-v1.0.0-rc.51 --output /path/to/results.json --concurrency 30 50 100 --profiles short long cap20 --seconds 20 --controls
```

本轮不包含真实互联网带宽、HTTPS/外层反向代理、图片音视频、大上下文、服务商 TPM/RPM、真实余额耗尽和长时间耐久压测。报告证明的是这台服务器上、此模拟协议和短时负载下的表现，尚不能给出生产最大并发或零延迟承诺。
